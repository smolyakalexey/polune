# Сущность «намерение» — продуктовая спецификация

Статус: базовый локальный цикл реализован 24 августа 2026; завершение, перенос и синхронизация остаются следующими этапами.

## Зачем она нужна

Сейчас Polune заканчивает работу в момент, когда пользователь увидел дату или открыл системный календарь. Намерение превращает разовый результат в продолжающийся план:

> я выбрал дело → согласился с датой → хочу вернуться к этому решению

В интерфейсе используем слово **план**. Термин **намерение** остаётся названием доменной сущности и продуктовой концепции.

## Граница сущности

Намерение хранит решение пользователя, а не новый астрологический расчёт.

Оно включает:

- выбранное дело;
- подтверждённую пользователем дату;
- состояние плана;
- снимок результата в момент сохранения;
- способ напоминания или календарного экспорта;
- историю явных переносов;
- желание подобрать следующую дату после завершения.

Оно не включает:

- копию даты, времени и места рождения;
- свободный пользовательский текст в первой версии;
- медицинские или другие чувствительные дела вне разрешённого каталога;
- автоматически изменённую дату после обновления методики;
- обещание, что событие обязательно произойдёт или пройдёт успешно.

## Предлагаемая модель данных

```ts
type IntentionStatus = "planned" | "completed" | "cancelled";

type IntentionReminder =
  | { kind: "none" }
  | {
      kind: "external_calendar";
      provider: "apple" | "google" | "unknown";
      lastAttemptedAt: string;
    };

type IntentionRepeat =
  | { kind: "none" }
  | { kind: "ask_after_completion" };

type IntentionSnapshot = {
  methodVersion: "0.6" | "0.7p";
  score: number;
  rating: "excellent" | "good" | "neutral" | "caution" | "low";
  personalizationLevel: "none" | "date" | "approximate" | "exact";
  verdict: string;
};

type IntentionDateChange = {
  fromDate: string;
  toDate: string;
  changedAt: string;
  reason: "user_selected" | "recommended_reschedule";
};

type SavedIntentionV1 = {
  schemaVersion: 1;
  id: string;
  intentId: string;
  selectedDate: string;
  status: IntentionStatus;
  snapshot: IntentionSnapshot;
  reminder: IntentionReminder;
  repeat: IntentionRepeat;
  dateHistory: IntentionDateChange[];
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
  cancelledAt?: string;
};
```

## Почему нужен снимок результата

Методика, персональный профиль или оценки будущих дат могут измениться. Пользователь должен видеть, на основании чего он сохранил план в тот момент.

- `selectedDate` остаётся неизменной до явного решения пользователя;
- `snapshot` объясняет первоначальный выбор;
- актуальный пересчёт можно показать отдельно как предложение;
- при переносе новая дата записывается в `dateHistory`, а снимок обновляется;
- изменение профиля рождения не переписывает историю задним числом.

Это предотвращает неприятный сценарий, когда приложение само меняет уже запланированную стрижку или поездку.

## Производные состояния интерфейса

Эти состояния не хранятся в данных, а вычисляются:

- **сегодня** — `selectedDate` совпадает с текущей московской датой;
- **скоро** — до даты осталось 1–3 дня;
- **в будущем** — дата позже;
- **требует решения** — дата прошла, но план всё ещё `planned`;
- **рекомендация обновилась** — актуальный пересчёт предлагает другую дату, но пользователь ещё не подтвердил перенос.

Просроченный план нельзя автоматически считать выполненным или отменённым.

## Состояния и переходы

```text
результат
   ↓ сохранить
planned ──→ completed
   │            │
   │ перенести  └──→ подобрать следующий план
   ↓
planned с новой датой
   │
   └──→ cancelled
```

Допустимые действия:

- `planned → completed` — пользователь подтвердил выполнение;
- `planned → cancelled` — пользователь отменил план;
- `planned → planned` — пользователь явно выбрал другую дату;
- `completed → новый planned` — для повторяющегося дела создаётся новая сущность, история завершённого плана не переписывается.

В первой версии не нужны состояния `draft`, `paused`, `deleted` и сложные серии повторений.

## Локальное хранение первой версии

- ключ: `polune-intentions-v1`;
- формат: массив `SavedIntentionV1[]`, даже когда бесплатная версия разрешает только один активный план;
- идентификатор: случайный UUID с тем же безопасным fallback, что уже используется для анонимной сессии;
- даты: календарные даты `YYYY-MM-DD`, время изменений — ISO UTC;
- при загрузке валидируется каждый элемент отдельно;
- некорректная запись пропускается, но не должна ломать остальные планы;
- изменение схемы требует нового `schemaVersion` и явной миграции.

Массив сразу готовит модель к нескольким планам и будущей синхронизации, не вынуждая менять формат после появления подписки.

## MVP-ограничение

Бесплатная локальная версия поддерживает:

- один активный план со статусом `planned`;
- любое количество локально завершённых/отменённых записей можно пока не показывать и ограничить короткой историей;
- повтор означает только `спросить о следующей дате после завершения`;
- напоминание выполняется системным календарём, собственного web-push пока нет.

Если пользователь сохраняет второе дело при существующем активном плане, первая проверяемая гипотеза — предложить:

1. заменить текущий план;
2. оставить текущий;
3. узнать о нескольких планах в будущей версии.

Это одновременно проверяет спрос на платную возможность нескольких активных планов.

## Рекомендуемый UX первой версии

### Сохранение

Основная кнопка итогового экрана называется `запланировать` и сохраняет намерение только внутри Polune. После сохранения показывается короткий полноэкранный success-сценарий: выбранная Луна и дата визуально попадают в календарь, затем доступны действия `на главную` и `добавить напоминание`. Возврат на главную сразу показывает карточку ближайшего плана и оставляет возможность выбрать новое дело.

Apple/Google Calendar больше не определяют факт сохранения плана. Они остаются отдельным вторичным действием для системного напоминания. Поэтому отменённый импорт `.ics` или закрытая форма Google не удаляют локальный план и не создают ложный статус.

### Повторный визит

На стартовом экране над основной CTA появляется компактный блок:

```text
ваш ближайший план
24 августа · постричься
посмотреть
```

Блок не должен превращать стартовый экран в dashboard. Основной выбор нового дела остаётся доступен.

### Карточка плана

По нажатию открывается существующий результат с сохранёнными `intentId` и `selectedDate`.

Дополнительные действия:

- `добавить в календарь` или повторить экспорт;
- `выбрать другую дату`;
- `выполнено`;
- `отменить план`;
- `подобрать следующую дату` после завершения, если включён повтор.

### После наступления даты

При следующем визите показываем короткий вопрос:

> получилось сделать задуманное?

Действия:

- `да` → завершить;
- `перенести` → показать следующую подходящую дату;
- `отменить` → закрыть план.

Не используем guilt-механику, серии и потерю прогресса.

## Пересчёт и персонализация

- сохранение плана не требует персонального профиля;
- план запоминает, использовалась ли версия `0.6` или `0.7p`;
- после добавления или изменения данных рождения текущая дата не меняется автоматически;
- если персональный пересчёт предлагает другую дату, показываем необязательное сообщение `появилась новая рекомендация`;
- перенос происходит только после подтверждения;
- удаление профиля рождения не удаляет сам план.

## Аналитика

Новые события-кандидаты:

- `intention_saved`;
- `intention_viewed`;
- `intention_reschedule_opened`;
- `intention_rescheduled`;
- `intention_completed`;
- `intention_cancelled`;
- `intention_repeated`;
- `second_intention_attempted`;
- `app_interest_viewed`;
- `app_interest_confirmed`.

Разрешённые свойства:

- `intentId`;
- `selectedDate`;
- `score`;
- `methodVersion`;
- `personalizationLevel`;
- `daysUntilDate`;
- `rescheduleCount`;
- `hasCalendarReminder`;
- `activeIntentionCount`.

Не отправляем данные рождения, место, пользовательские заметки или полный локальный идентификатор плана.

## Приватность и будущий аккаунт

- локальная версия не отправляет планы на сервер;
- до реализации нужно обновить страницу приватности и назвать новый localStorage-ключ;
- профиль рождения хранится отдельно и не копируется в план;
- при появлении аккаунта локальные планы импортируются только после явного согласия;
- серверная модель получает `ownerId`, но публичный URL результата не содержит идентификатор плана;
- удаление аккаунта должно удалять серверные планы, а очистка локальных данных — локальные.

## Проверки перед реализацией

1. Один и тот же `intentId + selectedDate` не создаёт дубликаты при повторном календарном экспорте.
2. Невалидная или прошедшая дата не создаёт новый план.
3. Наступившая дата не меняет статус автоматически.
4. Персональный пересчёт не меняет сохранённую дату.
5. Перенос обновляет дату только после подтверждения и сохраняет историю.
6. Повторный экспорт обновляет reminder, а не создаёт второй план.
7. Удаление профиля рождения не удаляет намерение.
8. localStorage недоступен — календарный экспорт продолжает работать без ошибки.
9. Старая или повреждённая схема не ломает стартовый экран.
10. Аналитика не содержит персональных данных.

## Принятые решения прототипа

- сохранять отдельным явным действием `запланировать` внутри Polune;
- завершённые планы хранить, но пока не показывать отдельной историей;
- при втором активном плане предложить заменить текущий или оставить его;
- показывать ближайший план на стартовом экране и в раскрытом календаре;
- не брать оплату и не просить аккаунт до проверки повторного использования;
- после success-сценария предлагать системный календарь только как напоминание.
